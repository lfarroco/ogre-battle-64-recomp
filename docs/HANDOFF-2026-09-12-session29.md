# Handoff — 2026-09-12 — session 29: the title runs at 30fps (a recompiler bug), and the cube's wall

> **Superseded in part by session 30** (`docs/HANDOFF-2026-09-12-session30.md`).
> The frame-rate work below stands. The "cube's wall" section does not: the
> records at `base+0x6C0` are created by `func_801A103C`, which state 9's init
> *does* reach — it was being compiled as a 2-instruction stub because splat had
> split off its prologue (`func_801A1034`). With that override, and 19 more for
> the same class of split, the records exist. Session 29's "needs streamed
> overlay banking" lead was a dead end: bank1's bytes at the state-9 entry
> points are mid-function, so overlay C is the correct resident overlay. See
> session 30 for the wall that remains.

## Outcome

Session 28 made the game render its own title scene, but at 2-8fps with
0.3-2.8s stalls: "low, inconsistent frame rate". This session found the cause,
and it was **neither the game nor the renderer — it was N64Recomp's poll-loop
heuristic emitting `yield_self` inside ordinary loops**.

Measured on the same machine and build type:

| | before | after |
|---|---|---|
| display lists in 8s | 8 | **171 in 6.2s** |
| median inter-frame gap | 20-50ms with 0.3-2.8s stalls | **34ms (~30fps)** |
| longest gap | 2816ms | **500ms (one scene load)** |

The game now plays the title at its intended 30fps and reaches its next wall:
a SIGSEGV at display list 171 (`func_801A1170` dereferences a NULL object) that
is caused by the **title's object table never being populated**. The "cube
falls into the middle of the soldiers" is the object table's content, so this
wall is what still hides it. The crash is pre-existing (the session-28 output
crashes at the same display list when run for 150s); the old frame rate simply
never got there.

## The bug: `yield_self` once per loop iteration

`OGRE_PROFILE=1` (new) samples every game thread's current recompiled function
and counts recompiled-function entries per thread. During a stall it showed the
hot thread was *not* in game math — `sample(1)` on the process put it in
`func_8008AFE0 → func_80072398 → func_800EAC24 → func_80081B08` with the samples
split between `yield_self` and `wait_for_resumed`. `func_80081B08` is a 36-entry
object scan, and the whole call took hundreds of ms, so it was yielding per
iteration. With an empty running queue `yield_self` sleeps until the next VI
retrace (~16.7ms), so a loop that yields per element runs at ~60 elements/s.

The heuristic (`tools/N64Recomp/src/recompilation.cpp`, `is_yield_poll_loop`)
had two holes that let ordinary loops through:

1. **The branch delay slot was excluded from the loop body.** The body was
   `[head_idx, instr_index)`, but the delay slot executes on every iteration:
   `bne $v0, $zero, head` / `addiu $v1, $v1, 0x13C` bumps the pointer *in the
   delay slot*, so `$v1` looked loop-invariant.
2. **A load's destination did not count as a write**, so a pointer chase
   (`lw $a0, 0x10($a0); bne $a0, $zero, head`) looked like `while (flag) ;`.
   The game's malloc free-list search (`func_80071A3C`) and the rest of the
   allocator family are exactly that, which is why the allocator "storm" seen in
   the session-18 snapshots was slow rather than busy.

### The fix

The loop body is now `[head_idx, instr_index + 2)` (the branch and its delay
slot), and `poll_base()` classifies a load as a poll load only when its base is
the constant produced by a `lui` earlier in the same iteration. A base
re-derived from a load (a pointer chase) is rejected; a base that is never
written in the body is still accepted. The classic spin
`lui $v0, 0x800E; lw $v0, 0x79A4($v0); bne $v0,$zero, ...` (`func_80089A10`)
is still detected — its base is written by `lui` immediately before the load.

```
# tools/N64Recomp/src/recompilation.cpp
size_t body_end = instr_index + 2;                    # was instr_index
...
auto poll_base = [&](size_t load_idx, int base) -> bool {
    if (base <= 0 || base >= 32 || nonconst_written[base]) return false;
    for (size_t j = load_idx; j-- > head_idx; ) {      # nearest write before the load
        ... writes = (rd==base) || (rt==base);
        if (writes) return jid == InstrId::cpu_lui;    # constant only if lui
    }
    return !load_written[base];                        # else reject pointer chases
};
```

`yield_self` sites in the generated code: **99 → 14**, and all 14 are real poll
loops (`func_80089A10`, `func_80075BC0`, `func_800997F0`, overlay polls, ...).
`RecompiledFuncs/` is gitignored and regenerated by `make recomp`;
`n64recomp-ob64.patch` was regenerated from the submodule diff.

### What was *not* the cause (both tested)

- **The renderer.** `processDisplayLists` is 0.6-8ms per display list.
- **The scheduler's `yield_self` implementation.** An osYieldThread-style
  version (hand off to the running-queue head before sleeping, instead of
  sleeping first) was written, measured, and **reverted**: with the recompiler
  fixed it changed nothing (171 display lists at 6.15s either way), so the
  change set stays focused on the actual root cause.

## The new wall: the object table is never filled

At **display list 171, t≈6.2s**, the game SIGSEGVs:

```
func_801A1170 + 674:  lbu $v0, 0x3($v1)      ; $v1 = *(entry) = NULL
  func_801A1FCC  (title draw)
  func_80177E08  (state 9 draw callback)
  func_80072398  (main loop)
```

`ctx->r17` (the entry pointer) is `0x801BAEE0 = D_801B81D0 + 0x770` — object
table **entry 11**. Entry 11 at the crash:

```
+0x770 pointer   = 0x00000000   <- NULL
+0x774 interp    = 0x0014       <- nonzero, so func_801A1170 proceeds
+0x776 duration  = 0x000C
+0x778 frame     = 0x0000
```

Entries are 0x10 bytes at `base + 0x6C0`, 13 of them, updated every frame by
`func_801A1B74` (interp = frame*255/duration) and spawned by `func_801A1328`.
`func_801A1170` uses `lh(entry+4)` as a "draw me" flag and `lw(entry+0)` as the
object pointer, so a nonzero interp with a NULL pointer is fatal.

### Why the pointer is NULL

Entries **10, 11 and 12** (and only those; the indexed ones 0-9 are created by
`func_801A1328`) are written by `func_801A103C` — and `func_801A103C` is called
from exactly one place: `func_8017B9C8`.

`func_8017B9C8` is the **draw callback of scene-state descriptors**
`0x8018FD70`/`D84`/`D98`/`DAC`, i.e. scene states 5-7. The dispatcher
(`func_80075BC0`, table `0x800AF028`) picks a descriptor by
`idx = hu(*(D_800C4BBC) + 4)`, and the game boots with `D_800E8214 = 9`
(set once at `0x800721F0`; bit `0x1000` of `D_800E79B0` would select 24, and
`D_800E79B0 = 0`). State 9's descriptor is `0x8018FB70`:

```
+0x00 func_80177DA0  start  -> func_801A1A2C (malloc 0x834 + zero)
+0x04 func_80177DCC  update -> func_801A1B74
+0x08 func_80177E08  draw   -> func_801A1FCC
+0x0C func_80177E40  exit   -> func_801A1AF4 (free)
```

Verified by instrumenting the generated code: in a 4-7s run
`func_80177DA0`=1, `func_80177DCC`=80, `func_80177E08`=81, `func_801A1B74`=81,
`func_801A0E44`=81, `func_801A0F3C`=81, and **`func_801A103C`=0,
`func_8017B9C8`=0, `func_80177E40`=0**. The state index never leaves 9.

So in state 9 the table is allocated, zeroed, animated and drawn, but never
filled. The twelve soldiers and the smoke render from the parallel
`func_801A0E44`/`func_8019FC68` path (which uses a different 0x90-byte object
array), while the cube — the table entries — has no object to draw. That is the
"cube should fall into the middle of the soldiers" gap.

### Session-29 follow-up on the cube (what the deeper dig found)

The state sequence was measured, not assumed. Instrumenting the dispatcher
(`func_80075BC0`, on state change) shows `9 -> 10` (state 9's update
`func_80177DCC` pushes `0x800A` once `func_801A1B74` returns 1, which happens
when its phase `D_801BA70C` reaches 4). A 6-minute run never leaves state 10;
states 5-7 are not reached on the normal path in that time. Forcing the boot
state to 5 or 24 (`D_800E8214`) SIGSEGVs during the first second, because those
states are **paging loaders**: `func_8017B60C`/`func_8017B6D0`/`func_8017B794`
DMA ROM `0x79750`/`0x87220`/`0x712A0` chunks into `0x8019A7C0` (overlay C) and
set the phase `D_801977E8` = 1/2/3; `func_8017B9C8` (their draw) then dispatches
on that phase, and phase 1 is what calls `func_801A103C`.

Two attempts to create the records from state 9 failed, both transparently:

* calling `func_801A103C` early in `func_801A1A2C` (state-9 start) fills all 13
  records with valid pointers (`0x801BFC60..`) but the first draw then
  SIGSEGVs inside `func_801A18A4 -> func_800924D0 -> func_800988A0` (matrix
  math), i.e. the records' models are not usable yet;
* calling it at the **end** of `func_801A1A2C` (after `func_80073164` /
  `func_8019F5C8` set up the DL buffer) does **not** crash but hangs the game
  after the boot list (1 display list).

That is consistent with the records' models coming from resource `0x322952`,
which is loaded by the states 5-7 paging path (their start callbacks' ROM DMAs),
not by state 9. State 9's own start (`func_8019EA64`) loads a different set:
a script block at `base+0x818` plus four effect models at `base+0x81C/820/824/828`
from ROM `0x1BA6094` (indices 0x74, 0xFF) and `0x1C2EC8C` (index 0x2A), used by
the effect/smoke path (`func_8019E7B0 -> func_8019E220` queries the `0x818`
block, magic `0x4D583300`, which is intact).

The game's own script (loaded into `base+0x82C`, advanced by `func_801A1328`;
~990 entries, opcodes 0-12) drives the whole intro: op11 sets the 12 soldier
animation records, op1/2/3 spawn effect objects (smoke puffs: types 17-20, each
a textured quad drawn by `func_8019E588`), op4/5/6 write the `0x6C0` texture
records, op8 triggers the soldiers' attack (`entry[0x4C] == 0xC` resets all 12),
op9/op12 fire sounds.

### A temporary unblock (not committed)

Guarding the NULL pointer in the generated `func_801A1170`
(`if (ctx->r3 == 0) goto L_801A131A;`) stops the SIGSEGV and lets the game run
indefinitely (200+ display lists, frames 32-44 show the impact smoke), but the
cube still does not appear, because the draw is then skipped. It was an
experiment only; `RecompiledFuncs/` has been regenerated clean.

### Leads for session 30

0. **The real blocker is streamed-overlay banking.** The three "states" are
   stages of the game's streamed-code loader and they page **different code**
   into the *same* RAM region. Verified against the ROM: the bytes that state 5
   DMAs to `0x8019A7C0` (ROM `0x79750`) are not the bytes the port has there
   (`streamedC` = ROM `0x1CE040` -> RAM `0x80197B90`; `streamedC`'s
   `0x8019A7C0` is `30A200F0 00822023 ...`, bank 1's is
   `27BDFFB0 3C04800F ...`). The game pages `0x712A0`, `0x79750` and `0x87220`
   over that region during the intro; `config.yaml` only defines **one** bank
   (`streamedC`, ROM `0x1CE040`), and the other three fall in the deliberately
   unconfigured gap `ROM 0x66E30..0x1CE040`. So `func_8017B9C8`'s call to
   `0x801A103C` executes whichever bank is loaded on hardware, but the port
   always links/CALLs `streamedC`'s function at that address. Extending the port
   to bank this region (splat segments + recompiled banks + runtime
   registration/`get_function` switching) is the actual fix for the cube, and it
   is Phase 4 work, not a renderer tweak.
1. **Reach states 5-7 properly once banking exists.** State 5's descriptor start
   (`func_8017B60C`) DMAs bank 1 and sets phase `D_801977E8 = 1`; the draw
   `func_8017B9C8` then calls `0x801A103C`, which (in that bank) creates the 13
   texture records. `func_8017B5DC` selects state 6's descriptor by
   `D_80193700`; the debug-menu path pushes `0x8006` at `0x80178AE0`.
2. **The record models are the cube and the N64 logo.** The script animates
   record 10 (`+0x760`) downward (op5 `a2=10, a6 += 3`), the fall; the crash is
   entry 11 (`+0x770`), which the bank-0 filler would have given model index 0.
3. **`func_8019F25C` + `func_801A18A4`** are the draw and matrix build that
   consume a record's texture, and both already run in state 9 today — only the
   record *content* is missing.



## Diagnostics added (all env-gated, off by default)

| knob | what it does |
|---|---|
| `OGRE_PROFILE=1` | sampling profiler: per-second per-thread dominant function, `entries/s` per thread, hot functions by entry count, plus `frame:` (retrace/last/acc/req/pend) and `bounds:` reads. `OGRE_PROFILE_CHAINS=1` also dumps live call chains. |
| `OGRE_TRACE_HOOKS=1` | keeps the per-function entry/return shadow-chain hooks on without the profiler. Off by default: they run on every recompiled function entry. |
| `OGRE_DL_TRACE=1` | prints every display-list submission with `trace_millis` and the recompiled-function entries spent on the frame. |
| `OGRE_DL_ANALYZE=1` | walks each submitted list with the app's own F3DEX2 analyzer and prints commands/triangles/texrects/textures. |
| `OGRE_VI_COUNT=1` | prints the number of VI-retrace messages (0x29A) delivered to the game, once a second (the frame-rate ceiling is half of it). |

`[sched-ring]` fixes: the dump compared `ev.seq` to the *slot index*, so every
event past the first 16384 was silently dropped (a wrapped ring printed only its
first 16384 events); it now compares to the global sequence the slot should hold.
Each event also carries a `trace_millis` timestamp.
